# Hardening a Cisco Migration-Assessment Toolkit: Parsing Robustness, Collection, Scoring, Architecture, and an Accessible Explorer

## TL;DR
- **The single highest-leverage change on the Python side is to make hand-rolled regex parsers defensively tolerant (anchor on stable tokens, treat fields as optional, never abort a run on one malformed device) and to validate them with golden-file/snapshot tests against captured `show`-output fixtures from IOS, IOS-XE, NX-OS, and IOS-XR — because cross-platform/version drift, not logic bugs, is the dominant failure mode for CLI scrapers.** Within the stdlib+netmiko+openpyxl constraint, the toolkit cannot adopt TextFSM/Genie as new dependencies, but it can borrow their patterns (named fields, per-command state machines, structured records) and can opportunistically consume NX-OS `| json` output (built into the device, no new Python library) where it already collects those commands.
- **The 0–100 Health Score and READY/CAUTION/NOT-READY verdict are methodologically defensible but currently uncalibrated; they should be treated as a transparent composite indicator and validated the way the OECD/JRC Handbook prescribes — documented weights, per-category caps to limit compensability, a one-at-a-time sensitivity sweep to show which weights actually flip verdicts, component-level breakdowns surfaced to users, and an explicit check that scores spread across bands rather than collapsing into "Critical" (the cry-wolf failure).** The per-category caps the author already added are exactly the right instinct.
- **For the Explorer, the next frontier beyond the prior layout/color redesign is accessibility and operational robustness: WCAG 2.2 AA conformance for the SVG graph (ARIA roles/labels, full keyboard navigation, a tabular data-equivalent, `prefers-reduced-motion`/`prefers-color-scheme`), graceful state handling without `localStorage` (which throws on `file://` opaque origins), URL-hash state sharing, schema-versioned snapshots with backward-compatible rendering, and sanitization of embedded topology/IP data before a single-file HTML deliverable leaves the building.**

---

## Key Findings

1. **Regex parsing is unavoidable here but must be engineered defensively.** The constraint (stdlib + netmiko + openpyxl) rules out TextFSM/ntc-templates and pyATS/Genie as imports. The mitigations are: anchor patterns on column headers and stable keywords rather than absolute positions; make every non-essential field optional; parse line-by-line with small per-command state machines; and wrap each device and each parse phase in try/except so one failure degrades gracefully.
2. **NX-OS gives you structured data for free.** Most NX-OS `show` commands support `| json` / `| json-pretty` (and `| xml`) natively on the device — no new Python dependency, parsed with stdlib `json`. This is the single biggest robustness win available within constraints for the Nexus portion of the fleet, with one well-known caveat (the `TABLE_/ROW_` single-vs-list ambiguity).
3. **Netmiko's API has moved decisively to `read_timeout`.** `delay_factor`/`global_delay_factor`/`max_loops` are deprecated and slated for removal in Netmiko 5.x; the toolkit should standardize on `read_timeout` plus the connection-establishment timeouts. Netmiko is synchronous/blocking, so concurrency must come from `ThreadPoolExecutor`, not asyncio.
4. **The scoring model needs validation, not redesign.** The architecture (weighted, per-category-capped deductions → banded score; checklist → verdict) is sound. What's missing is the OECD/JRC validation layer: sensitivity analysis, band-spread checking, and transparent component breakdowns.
5. **The Explorer's biggest unaddressed risks are accessibility, offline-storage failure modes, schema versioning, and data sanitization** — none of which the prior redesign report covered.

## Details

### Goal 1 — Cisco show-output parsing robustness (highest priority)

**Why structured approaches exist, and what to borrow.** TextFSM (a Google-originated template-based finite-state-machine parser) plus NetworkToCode's **ntc-templates** is the de-facto community standard for turning semi-structured CLI output into lists of dicts; Netmiko integrates it directly via `send_command(..., use_textfsm=True)`. (Kirk Byers documents that he "added support for direct TextFSM integration particularly for ntc-templates" in Netmiko 2.0.0; the exact December-2017 date could not be confirmed against a primary source — PyPI's earliest visible 2.x record is 2.0.2 on Feb 9, 2018 — so treat the year, not the day, as firm.) ntc-templates is a large, community-maintained repository (latest release **v9.1.0**, confirmed via GitHub Releases as "v9.1.0 Latest" published 01 Apr 2026 on a signed/Verified commit; the often-cited "~1,000+ templates / ~50 platforms / 283+ contributors" figures are widely repeated but could not be confirmed from a primary source and should be treated as approximate). Cisco's **pyATS/Genie** offers an alternative with hundreds of parsers returning nested dictionaries, plus the **Dq** (dictionary-query) helper for fluent querying (`output.q.contains('Established').get_values('neighbor')`), and — critically for an assessment tool — Genie can parse **saved text offline** via `device.parse(command, output=<string>)` against a mock device, no live connection required.

**But the toolkit cannot import these.** Given the hard constraint, the practical guidance is to (a) adopt their *design patterns* in hand-rolled parsers, and (b) opportunistically consume device-side structured output.

Concrete defensive-parsing patterns (all stdlib `re`):
- **Anchor on headers/keywords, not positions.** Cisco column layouts shift across platforms and versions; match on the header row to discover column boundaries, or match labeled key/value lines (`Root ID Priority 32768`) rather than fixed offsets.
- **Make fields optional and typed late.** Use non-capturing optional groups (`(?:...)?`) for fields that appear only on some platforms/versions (e.g., a `tunnel` interface type only added to some `show interface` templates). Keep raw strings; coerce to int/bool only at the record-construction boundary, inside try/except.
- **Per-command line state machines.** Mirror TextFSM: a tiny loop with `Start`/`Parse`/`Record` states per command is far more maintainable and resilient than one monster regex.
- **Tolerate locale/timestamps and banners.** IOS-XR prepends a timestamp line to command output (e.g., `Tue Nov 16 15:43:18.391 UTC`); strip leading non-data lines. Watch for `admin show platform` vs `show platform` producing different layouts on XR — a documented ntc-templates bug class.
- **Detect truncation and paging artifacts.** If `--More--` or a partial last line appears, flag the record as incomplete rather than silently parsing garbage. Always disable paging (`terminal length 0` on IOS/NX-OS; `terminal length 0` / `terminal width 0` on XR) before collecting.
- **Normalize interface names** to a canonical form (Gi/GigabitEthernet, Te/TenGigE, Eth/Ethernet, Po/Port-channel/Bundle-Ether) so cross-layer correlation joins succeed across platforms.

Commands that differ most across IOS / IOS-XE / NX-OS / IOS-XR (build per-platform parser variants and fixtures for each):
- **Interface status:** IOS `show interfaces status` (a switchport concept) has no direct NX-OS/XR equivalent in the same columns; NX-OS uses `show interface status` with different spacing; XR has no `status` form, use `show ipv4 interface brief` / `show interfaces`.
- **Spanning tree:** PVST+/Rapid-PVST output on IOS/NX-OS differs; NX-OS exposes structured `TABLE_tree/ROW_tree` via `| json`. XR generally does not run classic STP.
- **EtherChannel / port-channel:** IOS `show etherchannel summary` (flags column `SU`, `P`, `D`) vs NX-OS `show port-channel summary` (similar but distinct) vs XR bundles (`show bundle`).
- **CDP/LLDP neighbors:** column widths and truncation of long device IDs differ; prefer the `detail` variants for stable key/value parsing.
- **MAC address table:** IOS `show mac address-table` vs NX-OS `show mac address-table` (extra `Secure/NTFY` columns and per-VDC/VLAN nuances) vs XR `show l2vpn forwarding`/bridge-domain.
- **Routing table:** `show ip route` (IOS/NX-OS) vs `show route ipv4` (XR); VRF-awareness changes the header.
- **FHRP:** HSRP `show standby` (IOS) vs `show hsrp` (XR, with multiline IPv6 group quirks) vs NX-OS `show hsrp`; VRRP/GLBP each have their own forms.

**Free structured output (no new dependency):** For the NX-OS subset, if the toolkit already issues a command, it can issue `<command> | json` and parse with stdlib `json`. Caveat (Ivan Pepelnjak / Christopher Hart): NX-OS XML→JSON conversion makes `ROW_*` keys a **dict when there is one element and a list when there are many**; write a small normalizer that coerces every `ROW_*` to a list before iterating. NX-OS 9.3(1)+ adds **JSON Native** which preserves data types and is faster; the JSON output limit is 60 MB. IOS-XE's on-box `cli`/`clid` modules also return JSON but only when running *on* the device (Guestshell), so they are not usable from a remote netmiko session and are out of scope here.

### Goal 2 — Netmiko / collection best practices

**Timeouts and the `read_timeout` migration.** Netmiko 4.x replaced the old `delay_factor`/`global_delay_factor`/`max_loops` timing model with a single `read_timeout` (absolute timer on `send_command`, default 120s for timing-based reads / 10s for the prompt-pattern search). Netmiko's own deprecation warning states delay-factor compatibility "will be removed in Netmiko 5.x"; per-driver docstrings repeat "Deprecated in Netmiko 4.x. Will be eliminated in Netmiko 5." Set, per connection: `conn_timeout` (TCP connect), `auth_timeout`, `banner_timeout`, and per-command `read_timeout` sized to the slowest expected command (e.g., a large `show tech` or NX-OS `show interface` on a chassis with FEX can exceed 120s). The latest Netmiko release is **4.7.0** (confirmed via the PyPI netmiko project page: "This version 4.7.0 · May 12, 2026"; "Author: Kirk Byers · Requires: Python <4.0, >=3.10"), and the project is actively maintained by Kirk Byers.

**Autodetection.** `SSHDetect`/`ssh_autodetect` (set `device_type="autodetect"`, call `.autodetect()`) iterates `SSH_MAPPER_BASE` (~50 device types incl. Cisco IOS/IOS-XE/IOS-XR/NX-OS/ASA), caches command output, and returns the best match by priority. Useful when the inventory mixes platforms, but it costs an extra login round-trip; cache the result in the inventory so re-runs skip it.

**Paging and enable.** Netmiko disables paging automatically for known platforms (`terminal length 0`); for read-only assessment, prefer running without `enable` where `show` commands don't require it, and set the device account to a privilege level that can run `show` but not `configure` (audit/read-only safety).

**Concurrency — the key scaling decision.** Netmiko is synchronous/blocking (built on Paramiko), so **asyncio does not help**; the canonical pattern is `concurrent.futures.ThreadPoolExecutor`, one device per thread, collecting futures with `as_completed` and catching `NetmikoTimeoutException`/`NetmikoAuthenticationException` per future so one device's failure never aborts the batch. Practical worker counts are in the **5–10** range (commonly recommended in Netmiko tutorials and field practice; not a single authoritative spec), capped because most Cisco gear limits concurrent VTY/SSH sessions (often ~ a handful to ~15) and the collection server's own file-descriptor/CPU limits. Going past ~10–15 against the same management plane risks `No existing session`/banner-read failures (a documented Nornir+Netmiko symptom at `num_workers=50`). **Nornir** is the canonical inventory+concurrency framework (threaded runner, `num_workers`), and `nornir_netmiko` wraps Netmiko — worth recommending as a *future* path, but it is a new dependency and therefore out of scope for this constrained tool; the ThreadPoolExecutor pattern delivers the same concurrency within constraints.

**Credentials and read-only safety.** Never hard-code secrets. Read from environment variables (`os.environ["NETMIKO_PASSWORD"]`), an OS keyring, SSH keys, or a vault; support per-device credential lookup. Use a read-only/privilege-limited service account. Log structured per-device outcomes (success / auth-fail / timeout / parse-error) to a machine-readable log for the run report.

### Goal 3 — Health-score & migration-readiness model design and validation

**Treat the Health Score as a composite indicator and validate it the OECD/JRC way.** The authoritative reference is the OECD/European Commission-JRC *Handbook on Constructing Composite Indicators: Methodology and User Guide* (Nardo, Saisana, Saltelli, Tarantola; OECD, 2008, ISBN 978-92-64-04345-9, DOI 10.1787/9789264043466-en). Its ten steps and Step 7 in particular ("Robustness and sensitivity") map directly onto this problem:
- **Normalization before aggregation.** Each category's raw deductions should be normalized to a common scale before combining; the toolkit's per-category caps (L1 −30, L3 −30, cross-layer −45, protocol −25) are effectively a min-max bound that does this.
- **Weighting and the compensability problem.** Pure additive (linear) aggregation lets a strong category fully compensate for a catastrophic weakness — the Handbook's central warning. **Per-category caps are the right mitigation** because they prevent any one dimension from dominating and bound the damage a single category can do. Consider also flagging "any single category at its cap" as an automatic escalation regardless of total score (a partial move toward non-compensatory aggregation).
- **Robustness and sensitivity analysis (the most important missing piece).** The Handbook prescribes uncertainty + sensitivity analysis: it warns that "several judgement calls have to be made when constructing composite indicators, e.g. on the selection of indicators, data normalisation, weights and aggregation methods" and that "a combination of uncertainty and sensitivity analyses can help gauge the robustness of the composite indicator and improve transparency." Implement a simple **one-at-a-time (OAT) weight sweep** (±25%, ±50% on each category weight) plus band-threshold perturbation, and report **how many switches change band** under each perturbation. If verdicts are highly sensitive to an arbitrary weight, that weight needs justification or the threshold needs widening. This directly answers "which weights actually move verdicts."
- **Transparency / component breakdown.** The Handbook stresses that composite indicators can send misleading messages if opaque; always expose the per-category contributions (the deduction line items) next to the headline score so users can audit *why* a switch scored as it did. The Explorer's Health mode is the natural place for this.
- **Band-spread / "cry wolf" check.** A practical validation: run the scorer across the whole fleet and inspect the **distribution across Excellent/Good/Fair/Poor/Critical**. If nearly everything lands in Critical, the deductions are too aggressive and the tool will be ignored (alarm fatigue). Aim for a spread that discriminates; recalibrate caps/weights until the bands separate real outliers from the healthy majority. Document the observed distribution as an acceptance test.

**Risk-scoring framing.** The deduction model is implicitly a **likelihood × impact** scheme; make that explicit by weighting deductions by **asset criticality** (a core/distribution switch carrying many VLANs should weigh more than an access closet). Note the documented hazards of ordinal risk matrices (range compression, mathematically inconsistent ordinal arithmetic — see Graz University of Technology, "Problems with Risk Matrices Using Ordinal Scales," arXiv:2103.05440, which aims "to show the problems of qualitative risk assessment methods to argue towards quantitative methods"); since this score is at least interval-scaled and capped, it avoids the worst of those, but the team should not over-interpret small score differences as meaningful rank order.

**Migration-readiness checklist validation.** The 10-check pre-migration checklist aligns with established data-center/campus migration runbooks, which consistently emphasize: full hardware/software/asset inventory; application and L2/L3 dependency mapping; identification of mission-critical systems and priority tiers; pre-migration baseline/performance benchmarks to compare against post-migration; pilot/representative-subset testing before "big bang" (Phase 5 of the typical 10-phase runbook: "migrating a small, non-critical but representative subset of applications and infrastructure to test your entire process from end to end"); rollback/contingency plans; and a defined change/communication plan (ITIL change-readiness; Prosci ADKAR for the people side). NIST SP 800-88 is the reference for secure decommissioning of retired gear. Recommend explicitly mapping each of the 10 checks to one of these phases and adding any missing ones (notably: documented rollback plan, baseline capture, and dependency mapping) so the checklist is auditable against an external standard rather than ad hoc.

### Goal 4 — Python architecture, maintainability & correctness (single 5,700-line file)

**Decompose without adding runtime dependencies.** A single 5,769-line file can be split into a package of modules (`collect/`, `parse/`, `score/`, `report/`, `snapshot/`) using only the stdlib — module decomposition changes nothing about the dependency footprint. Separate the four concerns hard: **collection** (netmiko I/O), **parsing** (pure functions: raw text → records, no I/O), **scoring** (pure functions: records → score), **reporting** (openpyxl + JSON). Pure parse/score functions are trivially unit-testable and the win is disproportionate.

**Typing and data modeling.** Use `dataclasses` for records (interfaces, VLANs, neighbors, scores) and add type hints; run **mypy** in CI. Dataclasses give you stable field names that flow straight into the snapshot schema.

**Testing parsers (the highest-ROI testing investment).** Adopt **golden-file / snapshot testing**: capture real `show`-output fixtures from each platform/version into a fixtures directory, run parsers against them, and assert structured output matches a stored expected result. `pytest` parametrized over a directory of fixture cases is the idiomatic approach (the broader community uses plugins like pytest-golden / pytest-snapshot with an `--update-goldens`/`--snapshot-update` workflow to regenerate expected files; the *pattern* — not the plugin — is what matters and is reproducible with stdlib + a conftest fixture). Add a regression fixture every time a device breaks a parser. Consider property-based testing (hypothesis is a dependency, so optional) for tolerant numeric coercion.

**Tolerant, isolated error handling.** Wrap each device in try/except so one unreachable or malformed device logs an error and continues. Wrap each parse phase so a parser raising on unexpected output records a `parse_error` for that section but still emits the rest of the device's data. The Health Score should treat "data missing due to parse/collection failure" distinctly from "data present and bad" — otherwise a collection failure masquerades as a healthy or unhealthy device.

**openpyxl performance for large workbooks.** For large multi-sheet output, use **write-only mode** (`Workbook(write_only=True)`, create sheets with `create_sheet()`, append rows with `ws.append([...])`) which streams rows with near-constant memory; install **lxml** for speed (lxml is an openpyxl performance helper, not a new import in your code). Caveats from the openpyxl docs: a write-only workbook "can only be saved once" (a second save or append raises `WorkbookAlreadySaved`), sheets must be created before appending, and styling must be applied via `WriteOnlyCell` before append. Avoid per-cell `ws.cell(row, col).value=` assignment in hot loops — that per-cell overhead is the main openpyxl performance trap. If styling needs are heavy, batch them.

**Idempotency & config.** Make a run reproducible: a single config object (stdlib `argparse` + a JSON/INI config via stdlib `configparser`) for inventory, credentials source, command set, timeouts, worker count, and scoring weights/thresholds. Externalizing the **weights and band thresholds into config** (not hard-coded constants) is what makes the sensitivity analysis in Goal 3 practical and lets users recalibrate without editing code.

### Goal 5 — Extending the HTML Explorer research (new ground)

**Accessibility (WCAG 2.2 AA) for an SVG node-link diagram.** This is the largest unaddressed area. WCAG 2.2 (W3C Recommendation, October 5, 2023) AA is the current target. Specifics for the graph:
- **SVG semantics:** SVG 2 supports WAI-ARIA — give the root `<svg>` `role="img"` or `role="application"`/`role="group"` as appropriate, an `aria-label`/`<title>`, and `aria-describedby` pointing at a longer description. Per W3C's first rule of ARIA, prefer native semantics where possible.
- **Keyboard navigation:** node-link diagrams must be fully operable by keyboard (WCAG 2.1.1, no keyboard trap 2.1.2). Make nodes focusable (`tabindex="0"`), provide a logical focus order (2.4.3), arrow-key traversal between connected nodes, Enter/Space to activate, and Escape to exit a focused subgraph. Manage focus explicitly when modes change. (Note: the WAI-ARIA spec itself warns that `tabindex` correctness for graph/tree widgets is a common error condition — e.g., more than one item with `tabindex>=0`, or `aria-activedescendant` undefined when the container is focusable — so test the focus model carefully.)
- **Provide a tabular data-equivalent.** The most robust screen-reader strategy for a complex graph is a parallel, navigable HTML **table** of the same data (nodes, edges, health scores, findings) — Canvas/WebGL are "black boxes" to screen readers, and even SVG graphs are hard to consume aurally. A toggle between graph and table view (mirroring Grafana's Node Graph grid/graph switch) satisfies both sighted and AT users.
- **Color is never the only channel** (already addressed by the prior report's color+shape+label redundancy — good); ensure contrast ratios meet AA against the tinted-dark surfaces.
- **Motion & theme:** honor `prefers-reduced-motion` (disable layout animations/transitions) and `prefers-color-scheme`. Announce dynamic changes via an `aria-live` region (e.g., "Blast radius: 12 affected nodes").
- **Testing — and a realistic expectation of automated coverage:** automated tools find only a fraction of issues. Per Deque Systems' Automated Accessibility Coverage Report (2,000+ audits, 13,000+ pages, ~300,000 issues), "axe-core detected 57.38% of actual issues found in those audits" *by volume*, but by WCAG success-criteria count it covers only ~30% (roughly 15–16 of the 50 WCAG 2.1 AA criteria), and the UK Government Digital Service benchmark found the best automated tool detected only ~40% of known barriers. So combine axe-core/Lighthouse/WAVE with manual keyboard testing and a screen reader (NVDA: `NVDA+F7` lists landmarks/headings).

**Rendering performance at this scale and beyond.** SVG is the right call for the toolkit's scale and is well-supported for accessibility; the literature is consistent that **SVG degrades past a few thousand DOM elements** (rendering ~1,000 objects costs SVG ~10 ms vs Canvas ~1 ms; SVG "works beautifully up to a few thousand elements, then degrades quickly"). Practical thresholds and tactics:
- Keep SVG while node+edge element count stays in the low thousands.
- If a snapshot pushes past that, introduce a **Canvas overlay** for the dense edge layer while keeping interactive nodes in SVG (a documented hybrid: SVG for interactive/text elements, Canvas for the bulk). A peer-reviewed comparison (Horak et al., "Comparing Rendering Performance of Common Web Technologies for Large Graphs") found **flexible level-of-detail** (hiding labels/decorations when zoomed out) gives "a notable performance boost with a low implementation effort for SVG" — implement LoD before reaching for Canvas/WebGL.
- Use **event delegation** (one listener on the SVG root, not per-node), **debounce** pan/zoom and resize handlers, batch DOM writes inside `requestAnimationFrame`, and use `will-change`/transform-based pan to avoid layout/paint thrash.

**State management & persistence without libraries — and the `localStorage` trap.** A self-contained file opened via `file://` is an **opaque origin**, and `localStorage`/`sessionStorage` access from an opaque origin **throws `SecurityError`** ("localStorage is not available for opaque origins"; also blocked in sandboxed iframes without `allow-same-origin`). Therefore:
- Wrap any storage access in try/except and **feature-detect**; fall back to in-memory state.
- Use **URL-hash state** (`#mode=blast&node=...&filter=...`) for shareable/bookmarkable state — it works on `file://`, requires no storage permission, and makes deliverables reproducible. This is the recommended primary persistence channel for a single-file offline app.

**Modern topology/observability UI references (2024–2026).** Align patterns with: **Grafana Node Graph** (layered layout, arc sections on node borders to encode proportional metrics, grid/graph toggle, and a hard node cap — Grafana's docs state: "Node graphs can show only 1,500 nodes. If this limit is crossed a warning will be visible in upper right corner, and some nodes will be hidden." — a good model for the toolkit's own scale limits and for the score-as-arc idea); **Kibana** and **Cisco Catalyst Center / DNA** topology views; and observability service maps (X-Ray service map, Kiali for mesh). The arc-on-node-border idiom from Grafana is directly applicable to showing a switch's Health Score as a colored ring.

**Print / export for client deliverables.** Provide an **export-to-SVG** (serialize the live SVG DOM to a `.svg` file via a Blob + download link — pure vanilla) and an **export-to-PNG** (draw the SVG into a Canvas via an `Image`, then `canvas.toBlob()`). Add a `@media print` stylesheet that switches to the light theme, expands the current view, and prints the tabular data-equivalent alongside the graph. All of this is achievable with no external libraries.

**Testing a single-file vanilla-JS visualization.** Factor logic (layout math, scoring de-dup, state reducers) into pure functions exposed on a testable namespace so they can be exercised headlessly; smoke-test rendering by loading the file in a headless browser and asserting node/edge counts and ARIA attributes. Keep a few canonical snapshots (small/medium/large) as fixtures.

### Goal 6 — Cross-cutting: schema versioning, standards, security

**Version the snapshot schema and the consumer together.** Embed a `schema_version` (semantic version) in the JSON snapshot. The Explorer must **read the version and degrade gracefully**: render known fields, ignore unknown ones, and show a clear banner if the snapshot is newer than the explorer ("some features unavailable — please update the explorer") or older ("legacy snapshot — Health mode unavailable"). Keep additive changes backward-compatible (new optional fields), reserve major-version bumps for breaking changes, and keep a small migration shim that upconverts older snapshots to the current in-memory shape so old deliverables keep rendering. Because both artifacts ship together, tag releases so a given explorer build documents the snapshot versions it supports.

**Documentation/assessment deliverable standards.** Reference NIST guidance for migration risk management and SP 800-88 for media sanitization/decommissioning; align the readiness checklist phases to a recognized migration framework (e.g., Gartner's "6 R's" — Rehost, Replatform, Repurchase, Refactor, Retire, Retain — for disposition decisions) so the deliverable is defensible to auditors.

**Security of a topology-bearing HTML file.** A single-file explorer embeds potentially sensitive data (management IPs, hostnames, topology, possibly SNMP strings or other secrets if collected). Mitigations:
- **Sanitize before embedding:** strip/replace any credentials, SNMP community strings, TACACS/RADIUS keys, and pre-shared keys from collected config/output before they reach the snapshot. Maintain an explicit deny-list of fields and a regex scrub pass.
- **Offer an IP/hostname redaction/obfuscation mode** for snapshots that will be shared externally (consistent pseudonymization so topology still reads correctly).
- **No external calls:** confirm the file makes zero network requests (no web fonts, no CDN, no telemetry) — this is both a hard constraint and a data-exfiltration safeguard; a strict inline Content-Security-Policy `<meta>` can enforce it.
- **Treat the HTML as classified as the data it contains:** document handling expectations in the file itself and in the run report.

## Recommendations (prioritized, staged)

**Stage 1 — Robustness & correctness (do first; highest risk reduction)**
1. **Make parsers defensive and isolated.** Refactor each parser to anchor on headers/keywords, treat fields as optional, and wrap every device and every parse phase in try/except that records a typed error and continues. *Acceptance:* a deliberately malformed/partial fixture for each command no longer aborts the run and produces a `parse_error` record. *Benchmark:* a full run survives ≥1 unreachable device and ≥1 malformed device with complete output for all others.
2. **Stand up golden-file parser tests.** Capture real fixtures from IOS, IOS-XE, NX-OS, IOS-XR for every parsed command; add pytest cases asserting structured output. *Acceptance:* every parser has ≥1 fixture per platform it targets; CI fails on parser regressions.
3. **Consume NX-OS `| json` where already collecting.** For the Nexus subset, switch parsed commands to `<cmd> | json` + stdlib `json` + a `ROW_*`→list normalizer. *Acceptance:* NX-OS interface/STP/port-channel data comes from JSON, not regex, with the normalizer unit-tested. *Threshold to change course:* if a target command doesn't support JSON (`validate-json` fails), keep the defensive regex path.
4. **Standardize Netmiko on `read_timeout`** and per-connection `conn_timeout`/`auth_timeout`/`banner_timeout`; remove any `delay_factor`/`max_loops` usage. *Acceptance:* no DeprecationWarnings; slow commands sized with explicit `read_timeout`.

**Stage 2 — Scoring validation & transparency**
5. **Externalize weights/caps/thresholds to config** and add an **OAT sensitivity sweep** that reports how many switches change band under ±25%/±50% weight and threshold perturbations. *Acceptance:* a sensitivity report ships with each run; any verdict that flips under a small perturbation is flagged for review.
6. **Add a band-spread (cry-wolf) check** across the fleet and tune caps/weights until bands discriminate. *Acceptance:* not >~25% of a representative fleet lands in Critical unless genuinely warranted; distribution is reported.
7. **Surface per-category breakdowns** in Excel and the Explorer Health mode; weight deductions by **asset criticality**. *Acceptance:* every score shows its line-item contributions; core/distribution devices carry higher weight than access.
8. **Map the 10-check checklist to a recognized framework** and add any missing phases (rollback plan, baseline capture, dependency mapping). *Acceptance:* each check cites a phase; gaps closed.

**Stage 3 — Architecture & maintainability**
9. **Decompose the single file into a stdlib-only package** (collect/parse/score/report/snapshot) with dataclasses + type hints + mypy in CI. *Acceptance:* parse/score modules are pure and independently unit-tested; dependency footprint unchanged.
10. **Adopt openpyxl write-only mode** for large sheets; eliminate per-cell hot-loop writes; ensure lxml present. *Acceptance:* memory stays roughly flat on the largest workbook; generation time improves measurably.

**Stage 4 — Explorer accessibility, robustness, security**
11. **WCAG 2.2 AA pass:** ARIA roles/labels on the SVG, full keyboard navigation, a tabular data-equivalent toggle, `prefers-reduced-motion`/`prefers-color-scheme`, `aria-live` for mode changes. *Acceptance:* axe-core clean on automated checks; manual keyboard + NVDA pass; graph fully usable without a mouse.
12. **Fix offline state handling:** feature-detect `localStorage`, fall back to memory, and make **URL-hash the primary shareable state**. *Acceptance:* opening via `file://` throws no `SecurityError`; sharing a hash reproduces the view.
13. **Schema-version the snapshot + graceful degradation** in the explorer, with a migration shim for old snapshots. *Acceptance:* an older snapshot still renders (minus new features) with a clear banner; a newer snapshot warns rather than breaks.
14. **Sanitize and optionally redact** topology data before shipping; enforce zero external calls via inline CSP. *Acceptance:* no secrets in the snapshot (automated scrub + scan); optional pseudonymized export verified; no network requests on load.
15. **Add export-to-SVG/PNG and a print stylesheet**; introduce SVG level-of-detail before any Canvas overlay, and only add Canvas if element counts exceed the low-thousands. *Acceptance:* client-ready SVG/PNG export works offline; interaction stays at ~60fps on representative snapshots.

## Caveats
- **Version/coverage facts are time-stamped.** Netmiko 4.7.0 (PyPI: May 12, 2026), ntc-templates v9.1.0 (GitHub Releases: 01 Apr 2026), and pyATS/Genie's monthly 26.x cadence are current as of this writing but move fast; re-verify before relying on exact numbers. ntc-templates' exact total-template count and per-platform counts could not be confirmed from a primary source and are stated approximately; cisco_xr coverage is demonstrably thinner than cisco_ios (recent releases are still backfilling basic XR `show` commands that have long existed for IOS).
- **Constraint-bound advice.** All recommendations respect stdlib+netmiko+openpyxl (Python) and single-file/offline/no-external-libraries/no-web-fonts (HTML). TextFSM/ntc-templates, pyATS/Genie, and Nornir are referenced as *pattern sources and future options*, not as adoptions.
- **Scoring calibration is inherently judgmental.** Without a labelled dataset, the model can be made transparent, sensitivity-tested, and well-spread, but its absolute thresholds remain "defensible defaults." Sensitivity analysis tells you which knobs matter; it does not tell you the "true" weights. Treat scores as decision-support, not ground truth, and avoid over-interpreting small differences.
- **Device/version dependence.** Cross-platform command differences are extensive and not exhaustively enumerable here; the golden-fixture approach is the durable defense because it captures *your* fleet's actual output. NX-OS `| json` support and field names vary by release; always `validate-json` and unit-test the normalizer.
- **Performance thresholds are approximate.** The SVG-vs-Canvas crossover depends on element count, per-node complexity, and target hardware (mobile GPUs are weaker); measure on representative snapshots rather than assuming a fixed node count.
- **Automated accessibility coverage is partial.** Even the strongest automated tooling catches only a minority of WCAG success criteria (~30% by criteria count per Deque; ~40% of barriers per GDS); manual + assistive-technology testing is mandatory to claim AA conformance.
