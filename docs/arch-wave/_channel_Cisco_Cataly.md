# channel: Cisco Catalyst SD-WAN (vManage / "SD-WAN Manager") — the controller-based overlay (SD-WAN Manager + Validator/vBond + Controller/vSmart + WAN-edge IOS-XE/vEdge). The fabric state lives in the Manager's NMS database, NOT on the edge CLI, so device `show` text under-collects it; this is a controller-API channel, not an SSH channel. (Distinct from the ACI/APIC channel — keep them as two separate collectors sharing the JSON-ingestion plumbing.)

## channel
vManage northbound REST over HTTPS, base `https://<manager>:8443/dataservice/<...>` (default 8443; 443 on some deployments). Read path is plain GET (POST only for large alarm/event query bodies, GET-equivalent semantics). This is the documented, supported NMS API the GUI itself consumes — same `/dataservice` tree exposed at `https://<manager>/apidocs`. Realtime monitors are per-device (`?deviceId=<system-ip>`); aggregate/inventory and alarm/event objects are fleet-wide. Engine would loop: list devices once, then fan per-device realtime calls (mirrors today's per-device collect loop). NOTE distinction: aggregated/cached state (`/device/<...>` realtime, `/device/control/synced/...`) is read from the Manager's store (fast, no edge round-trip); a few `/device/...` realtime calls poll the live edge (slower, can time out on an unreachable node — handle as evidence-absent, not health).

## auth
Read-only, session-based. Two documented flows: (a) classic — `POST /j_security_check` (form-encoded `j_username`/`j_password`) → `JSESSIONID` cookie, then `GET /dataservice/client/token` → XSRF token sent as `X-XSRF-TOKEN` on every subsequent call; (b) `POST /jwt/login` (JSON body) → `token` + `csrf` claims. `POST /logout` to end. Collector must hold a dedicated service account whose role has "API access" permission; scope it to a built-in read-only/operator role (Manager RBAC supports custom read-only roles) so the token can GET monitoring/inventory/alarms but cannot push templates or config — this preserves the repo's read-only-by-default guardrail at the credential layer, not just by prompt. Secrets handled like the existing SSH creds (env/devices-file, never written to the snapshot). TLS verification on by default; allow an explicit `--insecure` only for self-signed lab Managers.

## key_objects

- GET /dataservice/device — fleet inventory + rollup health: deviceId, system-ip, host-name, device-model, version, site-id, uuid, board-serial, reachability(reachable|unreachable), status(normal|warning|error), state(green|yellow|red)+state_description, device-type/personality, controlConnections, bfdSessionsUp, certificate-validity, lastupdated/uptime-date (L3 identity + node health SSOT)
- GET /dataservice/system/device/controllers and /system/device/vedges — control-plane membership + lifecycle: deviceType, serialNumber, vmanageConnectionState, vedgeCertificateState, validity (reveals decommissioned-but-present / invalidated-cert / never-onboarded edges)
- GET /dataservice/device/control/connections?deviceId= and /device/control/connections/history — per-node control sessions: peer-type(vbond/vsmart/vmanage/vedge), local-status/remote-status(green|red), state(up|down), local-color, private/public-ip, protocol(dtls|tls) (L4 control-plane health). Also /device/control/synced/connections (Manager-cached) to avoid live edge polling
- GET /dataservice/troubleshooting/control/{uuid} — control detail incl. local-status-info/remote-status-info reason strings + is-preferred (root-cause text for a down control connection)
- GET /dataservice/device/bfd/sessions?deviceId= and /device/bfd/summary — data-plane tunnels (the SD-WAN 'fabric' L3/L4): src-ip, dst-ip, local/remote color, proto, state(up|down), uptime; down BFD = a site-pair overlay path is dead
- GET /dataservice/device/omp/peers?deviceId= and /device/omp/summary — overlay routing control: peer system-ip, type, state(up|down/Init), routes received/installed (OMP is the SD-WAN BGP-equivalent; a down OMP peer = no route advertisement)
- GET /dataservice/device/interface?deviceId= (+ /interface/synced) — L1/L2/L3 edge ports: ifname, if-admin-status, if-oper-status(up|down), ipv4-address, speed-mbps, mtu, rx/tx error+drop counters, vrf, encap (admin-up/oper-down = an err'd WAN/LAN circuit)
- GET /dataservice/device/system/status?deviceId= and /device/hardware/environment — platform/L1 health: mem_used/total, cpu (user/system/idle), disk, uptime; environment PSU/fan/temperature status (degraded-but-present hardware)
- GET /dataservice/alarms (POST {query:{condition,rules:[{field:'entry_time',operator:'last_n_hours',value:['24']}]},size} for large windows) + /alarms/fields — active fault objects: severity(Critical|Major|Minor), severity_number, active(true), acknowledged, component, rulename/rule_name_display, system_ip, devices[], entry_time, eventname, cleared (the fleet-level firing-fault feed)
- GET /dataservice/certificate/vedge/list and /device/counters — cert validity + per-device control/BFD/expected-vs-actual counters (e.g. expectedControlConnections vs actualControlConnectionsToVsmart) for the 'fewer tunnels than designed' detector

## parser_strategy
The architectural delta is real: today's pipeline is text-only — `cmd_to_file: Dict[str,str]` (command-string → on-disk show-output file), `cmdio._load_cmd_output` reads the file and screens Cisco error banners, and ~70 `parse_*(text)->dict` functions in parse.py turn strings into model dicts that build.py assembles per device. JSON breaks two assumptions: there is no `.txt` file per command and no text to regex. Plug-in plan that minimizes disturbance: (1) NEW module `cisco_toolkit/sdwan_collect.py` — the only network-touching code: authenticate, GET the key_objects, and WRITE each JSON response to disk as `<deviceId>__<object>.json` under a `sdwan_collection_<stamp>/` dir, so an offline re-analyze (`--no-collect --collection-dir`) works exactly like today and the live call is isolated and skippable (mirrors `collect()` vs the offline loop). (2) NEW `cisco_toolkit/sdwan_parse.py` — pure functions `parse_sdwan_devices(obj)`, `parse_control_connections(obj)`, `parse_bfd_sessions(obj)`, `parse_omp_peers(obj)`, `parse_sdwan_interfaces(obj)`, `parse_sdwan_alarms(obj)`, each taking ALREADY-DESERIALIZED dict/list (not text) and returning the same normalized record shapes the snapshot uses; wrap them in `_safe_parse` for the existing fail-soft contract. A thin `_load_json_object(dir, deviceId, obj)` mirrors `_load_cmd_output` (skip empty/`{error:...}` Manager payloads the way `_CISCO_ERRORS` skips banners). (3) build.py grows `build_sdwan(collection_dir)->dict` that assembles a new top-level evidence axis `snap["sdwan"] = {devices, control_connections, bfd, omp, interfaces, alarms, coverage}` — additive, parallel to `vpc`/`service_map`, EXCLUDED from the frozen golden like the other compute_* axes so no snapshot churn. (4) analyze/detector layer needs NO new machinery: extend `design_advisor._signals(snap)` to read `snap['sdwan']` into flat `sig['sdwan_*']` counts, and add `_d_sdwan_*(snap, sig)` detectors following the exact `if <broken-count> <= 0: return None` / `_decision(..., priority=, evidence_citations=[...], devices=[...])` contract already used by `_d_vpc_health`/`_d_nve_peer_health`. Deliverables (workbook/explorer/HLD) inherit it because they read the snapshot. Net: one new collector + one new JSON-parser module + one build axis + N detectors; the build→analyze→detector→deliverable spine is untouched. (Reuse: factor the JSON-file load/screen helper so the planned APIC/ACI channel shares it — both are 'authenticated REST → JSON-on-disk → parse dict' and should not fork the plumbing.)

## firing_findings

- sdwan-control-connection-down (Critical/High): a WAN-edge or controller has a control connection in state=down OR local-status/remote-status=red — fires per affected peer, citing troubleshooting/control local-status-info reason; means that node is cut off from the controller (no template/policy push, OMP isolation). Coverage-honest: silent when all observed connections are up; never fires from absence of the object.
- sdwan-expected-vs-actual-control-deficit (High): actualControlConnectionsToVsmart < expectedControlConnections (from /device/counters) — the node has FEWER controller sessions than its design calls for (partial control-plane redundancy loss) even while 'up'. Broken-state, not absence.
- sdwan-bfd-tunnel-down (High): a BFD data-plane session state=down between two sites — that overlay path/SLA class is dead; fires per down src/dst+color tuple, citing /device/bfd/sessions. Distinguishes a real down tunnel from a site that simply has no tunnels configured.
- sdwan-omp-peer-down (High): an OMP peer state != up (down/Init) — overlay routes are not being exchanged with that peer; cite /device/omp/peers. (The SD-WAN analogue of a dropped BGP session the engine already flags.)
- sdwan-node-unreachable-in-fabric (High): /dataservice/device reachability=unreachable or status=error/state=red while the node is still an inventoried fabric member — a present-but-broken edge (NOT 'we failed to poll it'; grounded in the Manager's own reachability verdict).
- sdwan-decommissioned-but-present / cert-invalidated (Medium-High): a controllers/vedges entry with vedgeCertificateState=invalid|expired or validity=invalid|staging while still listed — an edge whose trust is revoked but the object lingers (security + migration-inventory hazard). Fires on the broken state, never on 'no cert data'.
- sdwan-active-fault (severity-mapped): each ACTIVE, non-cleared /dataservice/alarms record mapped to the engine's bands — Critical→Critical, Major→High, Minor→Medium — keyed by system_ip+rulename so it joins the per-device dossier; only active=true,cleared=false alarms fire (cleared alarms are evidence, not findings).
- sdwan-template-out-of-sync (Medium): a device whose configOperationMode/template-status indicates out-of-sync / config-drift vs the attached template (from device + template-attach status) — running config has diverged from intended; a real broken state, surfaced only when the Manager reports the mismatch.
- sdwan-edge-interface-admin-up-oper-down (Medium-High): if-admin-status=up & if-oper-status=down on a WAN/LAN edge interface (from /device/interface) — an enabled circuit that is dark; per-interface, error-counter-corroborated. Mirrors the existing err-disabled/down-portchannel detectors.
- sdwan-environment-degraded (Medium): a PSU/fan/temperature sensor in a non-OK state from /device/hardware/environment on a present node — degraded-but-running hardware, not a missing reading.

## effort
Medium — roughly 2-3 focused build-waves (~1500-2500 LoC across sdwan_collect.py + sdwan_parse.py + build axis + ~8-10 detectors + tests/fixtures + 1-2 deliverable surfacings). The pure-function parse/detect/deliver parts are fast and test-first against canned JSON fixtures (no lab needed). BIGGEST ARCHITECTURAL RISK: the engine is built end-to-end on the text/`cmd_to_file`/`_load_cmd_output` assumption — a controller channel introduces a genuinely different ingestion mode (live authenticated HTTPS session + JSON, multi-call session state, token/CSRF lifecycle, per-device fan-out with timeouts/pagination) that has no analogue today; the temptation to bolt JSON onto the show-text path will create a mess. Secondary risks: (a) no lab Manager to capture ground-truth payloads → field-name drift across releases (20.x vs 26.1) since responses are version-sensitive and some fields are undocumented — must pin to a tested release and degrade-gracefully on missing keys; (b) live collection violates the offline/read-only spirit unless the read-only RBAC role + offline JSON-replay are enforced from day one; (c) per-device realtime calls can be slow/rate-limited on large fabrics (bulk API exists but is heavier). Mitigation is structural: keep the network code quarantined in sdwan_collect.py and make everything downstream consume JSON-on-disk, exactly like the offline show-text replay.

## recommendation
Build it next — but as a small, quarantined first slice, because it is the cleanest path to making a whole class of customer (controller-based WAN) assessable, and it de-risks the parallel ACI/APIC channel by establishing the shared 'authenticated REST → JSON-on-disk → dict-parser → snapshot axis → coverage-honest detector' pattern once. SMALLEST VIABLE FIRST SLICE (one wave, fixture-driven, no lab dependency): (1) sdwan_collect.py that authenticates and dumps ONLY THREE objects to JSON-on-disk — GET /dataservice/device (inventory+health), /device/control/connections (control plane), /dataservice/alarms (active faults); (2) sdwan_parse.py with the three matching pure dict-parsers + the bare-array/{data:[]} dual-shape loader; (3) build_sdwan() attaching snap['sdwan'] (excluded from golden); (4) THREE detectors — sdwan-control-connection-down, sdwan-node-unreachable-in-fabric, sdwan-active-fault(severity-mapped) — wired through _signals/_d_* exactly like _d_vpc_health, each with the `<=0: return None` honesty gate; (5) tests against canned JSON fixtures (one healthy fabric, one with a down control connection + a Critical alarm) proving the detectors fire on broken-state and stay silent on clean/absent. Defer BFD/OMP/interface/environment/template-sync detectors and any live-fabric integration to wave 2 once the JSON spine and the read-only RBAC service-account story are proven. Do NOT ship any write/template/config-push capability — keep the channel strictly GET, behind a read-only role, with offline JSON-replay as the default analysis path.
