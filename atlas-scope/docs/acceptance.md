# Atlas Scope — Acceptance Criteria

The exit condition for the build loop. Every criterion is checkable by someone who did not write
the code. A criterion is met only when its **evidence** column can be produced on demand.

Grading vocabulary: **PASS** (evidence produced), **FAIL** (evidence contradicts), **UNPROVEN**
(no evidence either way — counts as FAIL for release purposes, because an unexercised gate is not
a gate).

### E4 is replicated, and records how busy the host was

An external audit ran `measure-fps.mjs` fifteen times against one unchanged `dist/` build and got 40.46–60 fps — FAIL, PASS, NOT MEASURED and PASS again, with no code change between them. Every FAIL coincided with other processes on the box; the five consecutive passes were the five runs taken under 25 % host CPU. A single invocation therefore decided the criterion on a property of the machine, and nothing in the report envelope recorded that property, so a green result could not be told from a lucky one.

The gate is now the median across the run's own ten sample windows, it refuses a verdict on fewer than five usable windows, no single window may fall below a stated 45 fps floor, and the report carries `hostQuiescence.busyFractionOfRun` measured from the OS scheduler's counters across the measurement. `acceptanceEvidence: true` requires a PASS **and** a quiet host. A figure taken on a contended machine may still be quoted — as a measurement of that machine.

### E4's 45–55 fps band is reported, not stepped

The step-down rule (`src/fabric3d/stepdown.ts`) moves the tier only below 45 fps or at ≥ 25 % slow frames, deliberately: a tier change is the most expensive thing the fabric does, and raising the rule to 55 fps would drive a display refresh-limited under 55 Hz (a 50 Hz panel, a remote-desktop session) to `low` for good, since no tier renders faster than the display presents. But that band used to be SILENT — measured 2026-09-22, an 8 s continuous orbit drag rendered at 53.9–54.5 fps with the tier at `high` and `qualityReasons` saying only "full quality". It is now tracked on its own (`createFrameRateBar`): below 55 fps over a 2 s window of drawn frames raises `stats().frameRateBelowBar`, puts the measured rate in `qualityReasons`, and the permanent status line reads "below frame-rate bar" beside the tier. It clears at 56 fps, and on a tier change. A below-bar orbit is still an E4 FAIL in `measure-fps.mjs`; it is simply no longer an unreported one.

### E3's scope: interactions, not navigations or window resizes

E3 is judged on the five declared journeys (E1), and **a declared journey is exactly what `review/measure-inp.mjs` times** (decided 2026-09-23 on the owner's delegated authority): every input a journey's measured act performs belongs to that journey, so a task over 50 ms on any of them is an E3 violation. This makes E3 stricter, not looser — the first finding selection after load, path-trace swap, and the palette's close are E3 subjects because the journeys time them. `review/audit-e5-sweep.mjs` times only inputs no journey's act performs; where an action needs a journey's input to reach its own state (the palette open before running a command, a grid click before arrowing through it, typing the filter it then clears), that input is the action's untimed `setup`, run before its measured window opens. `src/core/journey-scope.test.ts` derives both sides from the two files — it executes every journey act and every sweep action against a recording page and fails if a sweep action performs an input a journey's act performs — and requires the two lists below to be exactly the harnesses' own ids and action names, so this declaration cannot drift from what is measured. Until 2026-09-23 it had: the sweep re-timed J4's swap+submit and J1's first selection under "outside" names, and this paragraph listed both, plus the palette open, as outside the journeys while also saying the first selection was inside J1.

### E4, restated — why "1920×1080 with a trace animating" was not checkable as written

Two words in the original criterion could not be evidenced, and both are corrected above rather than
quietly satisfied.

**"A trace animating."** The packet only runs when the stitched path has non-zero length, which needs
at least two hops joined by a cable (`src/fabric3d/flow.ts`: `acc.length < 6` ⇒ `totalLength = 0`,
`packetRunning = !reducedMotion && totalLength > 0`). Measured over the product's own
`suggestedFlows()` + `traceFlow()` on this snapshot: every flow returns **one hop**, and one returns
none. So no reachable state animates a packet, and a 60 fps figure taken on a `?flow=` page is a
measurement of an **idle rAF loop with the renderer doing nothing** — the dirty flag is clear, the
loop ticks at the display rate, and nothing is drawn. Whether multi-hop traces should exist is a
question for the forwarding engine (A2/A5), not for this criterion.

The criterion therefore asks for a render condition that is **established and named**:
`review/measure-fps.mjs` prefers the trace packet, falls back to sustained camera motion — the
product's own focus-to-device affordance — and records which one it used. Every sample is gated on
`stats().converged === false`: a window the scene spent converged is reported **NOT MEASURED**, never
as a frame rate. Verified by removing the camera motion from a copy of the harness: it still reads
"mean 60 fps" off the idle loop and the gate answers `NOT MEASURED — the sample window was rendering
only 0% of the time`, exit 1.

**"At 1920×1080."** That is the **viewport**, not the render target. At a 1920×1080 viewport the
fabric is one region of a simultaneous four-surface layout and its canvas is **1160×962** — 1.12 MPix,
not 2.07 — at `devicePixelRatio` 1. No figure in this repository has been taken with the fabric
filling a 1920×1080 render target, and the reference machine's physical panel is 1280×800, so that
viewport is emulated in every run. Canvas CSS size, drawing-buffer size, device pixel ratio and
megapixels are now recorded beside every frame-rate figure, and `ATLAS_FULLBLEED=1` measures the
wider layout the product itself produces below 1024 px. A figure without its render target is not
evidence for this criterion.

## The blind comparison protocol (criterion C1)

This is the user's explicit bar and it decides when the loop stops.

1. Capture Atlas Scope in the seven investigation states, both themes, both viewports.
2. Capture the reference products at the same viewport.
3. Present a critic **two images with no identifying labels** — ours and a reference — and ask
   which is the better professional tool interface, and why, in specifics.
4. The critic must not be told which is which, and must not have built either.
5. Record the verdict and the specific reasons. **Every reason ours loses becomes a work item.**
6. Repeat until ours wins or ties on every pairing, with at least two independent critics agreeing.

A critic who cannot articulate a specific, actionable reason for its preference has not done the
job and its verdict is discarded.

**Protocol additions (phases 3 and 3.5, recorded 2026-09-30).** These tighten the steps above; none
relaxes them.
- **Recognition is asked first.** Before the verdict the critic is asked whether it recognises the
  product, vendor or brand of either panel, and if so to name it and the panel. A critic who recognises a
  product is excluded and reported separately. Critics are independent: a fresh context, no access to the
  repository or the design brief; a human or a different model family is preferred, and the critic's
  model is recorded.
- **Pairings are matched by task on both panels, one pairing per dimension,** through one vocabulary
  (`review/blind-pair.mjs` `TASK_KINDS`); our state is checked inside the crop the critic sees, and both
  panels carry neutral masks over every identity mark (ours measured in our DOM and checked by OCR).
  Current pairings: composition — our blocked path against Forward's dropped path; information density —
  our finding drill against Forward's vulnerability table; typographic craft — our blocked path with the
  hop's evidence open against IP Fabric's path detail; colour discipline — our raw evidence record
  against Grafana Explore; network visualisation — our drawn 2-hop trace against Forward's topology path.
  Whether "the 3-D render" stays in C1 on that basis or moves to C5 is an owner decision.
- **The pre-registered rule is `review/blind-pair.mjs` RULE v4** (ruleSha `939de74c18c5…`), and its
  executable proof is `review/blind-pair.mjs --selftest`. A pairing is PASS only when at least two
  distinct, unrecognising, reasoned verdicts bound to the current build pick ours or a tie and no counted
  or uncounted verdict may pick the reference; otherwise UNPROVEN. A critic's first line decides its
  verdict and its recognition; a later line can drop a win but never a loss; an answer that is not A, B
  or tie counts as a possible loss; critic ids and picks are normalised for Unicode, case and spacing, and
  a line that cannot be tied to a critic is never counted and still blocks when it may pick the
  reference. **A loss is never erased for that build.** C1 is PASS only when every pairing is PASS.
- **"Repeat until ours wins" (step 6) means repeat after the losing reasons are fixed in a NEW build** —
  never re-asking critics about the same build until a pass appears.
- **Known gaps before any panel counts (`docs/open-issues.md` O70):** the validator still loses a loss
  stored under a variant dimension key, one whose sheet reference is not the exact current sha, and one
  from a critic that names a product while answering `recognized: false`; our panel is a crop on three
  pairings, and the panels say so.
